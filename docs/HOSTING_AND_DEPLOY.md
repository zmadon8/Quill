# Hosting and Deploying the Judgment Diary

Written for someone who does not code. Prices are approximate and should be checked on the provider's website before you sign up. This is a recommendation; it depends on the open question in `docs/DESIGN.md` about the combined app. If the combined app already has a host, use that host.

## 1. Recommendation in one paragraph

Use **Render** with three paid pieces: one **Web Service** (the website), one **managed PostgreSQL database** (where your notes live), and one small **Cron Job** (a scheduled task that makes the nightly backup). All three are described in the file `render.yaml` in the project, so Render can create them in one go (a "Blueprint"). Expect about **US$15 to $18 a month** in total (roughly $7 for the web service, $6 to $8 for the smallest paid database, and a few dollars at most for the cron job; confirm on Render's pricing page). **Railway** is a reasonable alternative with similar cost and similar steps.

## 2. Why paid, and what to avoid

- **Avoid free databases.** Free databases on most hosts are deleted or paused after a short time. Your life's work cannot sit on that.
- **Avoid free web services.** They go to sleep when unused and take a long time to wake, which is annoying and can look like a failure.
- **Never store data on the server's disk.** On these hosts, the disk is wiped at every update. Everything goes into the database. The app is built this way (and the design forbids files on disk).
- Your data (about 950 Items) is tiny. The cheapest paid tiers are plenty. You pay for **reliability**, not size.

## 3. Two layers of backup

Backups are your safety net, so there are two independent layers.

1. **The host's database backups.** Render's paid databases keep automatic backups and allow recovery to an earlier point in time (the length of time depends on the plan; check the plan page). This protects against host or database trouble.
2. **The app's own nightly backup.** Every night the scheduled Cron Job creates a full machine-readable backup (in Milestone 0 this covers the user accounts; the diary data is added as it is built). The backups are stored **inside the database**, so they are also covered by the host's database backups. The app keeps **at least 30 days**. You can **download any of them** from the Backups screen, and you can restore from one. Before a restore the app shows a **preview** of what would change, and it takes a **safety backup** of the current data first.
3. **Off-site copy (planned, not built yet).** A later milestone may send each nightly file to a separate storage service, such as **Backblaze B2** or **Cloudflare R2** (pennies per month). Until then, use habit 4 below.
4. **Your own habit:** download a backup to your computer once a month and keep it somewhere you control (for example a USB drive or your own cloud folder).

The Backups screen shows when the last backup ran and whether it worked. If a night's backup fails, the app shows a warning at the top of every page.

## 4. First-time setup outline (done once, with Kiro's help)

You will need: an email address, a payment card, and a GitHub account (the project already lives on GitHub).

1. **Create a Render account** at render.com using your email. Add a payment card.
2. **Connect Render to GitHub.** Render asks permission to see the Judgment Diary project. Give access to that project only.
3. **Create everything from the Blueprint.** In Render choose New, then Blueprint, pick the Judgment Diary project and the branch to deploy. Render reads `render.yaml` and shows the three pieces it will create (database, website, nightly backup job), all on paid plans. Do not change a plan to Free.
4. **Fill in what Render asks for.** The secret key is generated by Render. The only thing it may ask you to type is the optional list of web addresses (`DJANGO_ALLOWED_HOSTS`); leave it empty unless you have your own domain. The database address is connected automatically. Nothing secret is ever put in GitHub. The full list is in the README.
5. **Wait for the first deploy.** Render builds and starts the site, then gives you an address. Open it. You should see the login page.
6. **Create your Admin account.** Open the web service in Render, open its Shell tab, and run `DJANGO_SUPERUSER_USERNAME=yourname DJANGO_SUPERUSER_PASSWORD='a long password' python manage.py create_first_admin`. This works only when there are no users at all, so it cannot be misused later. (Or run `python manage.py create_first_admin` with the username only and type the password when asked.) Store the password in a password manager.
7. **Log in** and create a second user in the Users screen.
8. **Custom address (optional).** If you own a domain name, Render shows you where to point it. https (the padlock) is automatic.
9. **Check the nightly backup.** It is switched on automatically by the cron job from the Blueprint; there is no switch in the app. The next morning, open the Backups screen and confirm a new "Daily" backup appears. You can also press "Backup now" at any time. The same job then runs `python manage.py refresh_offline_copies` to remake the saved copy behind each secret Offline link; you can run it by hand in the Render shell.
10. **Do a restore rehearsal** on a practice copy before putting real data in: download a backup, restore it, and confirm it works. Only then is the system ready for the real Word import.

## 5. How to deploy a change (every time)

You do not touch code. The steps are:

1. **You ask Kiro** for the change in plain words.
2. **Kiro makes the change and opens a "pull request"** on GitHub. This is a request that says "please add this change". Nothing is live yet. Kiro explains what changed and how to check it.
3. **You look at it.** Where possible Kiro provides a test copy of the site (a preview) so you can try it first.
4. **You click the green Merge button** on the pull request page on GitHub. This is your approval. If you are not sure, do not click it; ask Kiro.
5. **Render notices and updates the live site automatically.** It takes a few minutes. Render shows "Live" when finished.
6. **Backup before a database change.** If a change alters how the data is stored (called a "migration"), the update step (`migrate_with_backup`) automatically takes a "Before update" backup first, and stops the update if that backup fails. Kiro will tell you in the pull request. Before you click Merge on those, you can also press "Backup now" in the Backups screen and download the file.
7. **Check the site.** Open it, and check the thing that changed. Look at a couple of familiar Subjects to be sure all is as before.
8. **If something is wrong, roll back.** In Render, open the web service, go to Events or Deploys, find the previous good deploy and press **Rollback** (or Redeploy on the earlier one). This restores the previous version of the program in a minute or two. It does not change the data. If the data was changed by a migration, tell Kiro and restore from the pre-change backup (with the preview) instead.

## 5b. If the deploy stops with "Items still sit beneath another Item"

**What it meant.** The update turns old Nested Items into ordinary Items with several citations. Its last safety check found Items that still sat beneath another Item, so it stopped and **rolled everything back**. Nothing was lost or changed: your data is exactly as before, and the old version of the site kept running.

**What was fixed.** The conversion now handles every Item that has Items beneath it, however it was nested, including Items already in Trash. The check itself is unchanged.

**Optional look first (changes nothing).** In the Render Shell of the running service: `python manage.py nested_report`. It lists each Item that sits beneath another Item and what the update will do with it.

**To redeploy.** Merge the fix, then deploy as in section 5. The backup `pre_migration` is taken first as usual. If it stops again, copy the error line and send it; the data will again be untouched.

## 5c. Releasing the Fee Register (/fees/)

The Fee Register ships dark: `render.yaml` sets `FEES_ENABLED` to `0`, so every `/fees/` address is "not found" and no button or tab shows, while its tables, backups and restores keep working. At the owner's go-ahead:

1. **Merge** the pull request. Render deploys it; the update step `migrate_with_backup` takes a "Before update" backup first and stops if it fails.
2. In Render, open the web service, **Environment**, set `FEES_ENABLED` to `1` (and change the value in `render.yaml` so the next Blueprint sync does not set it back to `0`). It redeploys.
3. **Once**, in the web service **Shell**:

   ```
   python manage.py create_fees_user --username Ziyad --profile Ziyad-Fees --make-admin
   ```

   This only attaches the `Ziyad-Fees` profile and its membership to the existing user `Ziyad`. It creates no user.
4. Log in as Ziyad, open **Fees**, then **Settings > Backup** and restore the desktop backup. Compare the key figures (KPIs) with the desktop program.
5. Optional checks in the Shell: `python manage.py fees_check` (read-only, prints any memo whose stored totals disagree with a recomputation) and, to measure memory with the real instance, `python manage.py fees_memory_bench` (uses a throwaway profile, leaves no data; see `docs/FEES_RAM_BUDGET.md`).

`FEES_ENABLED` when not set: on for developer mode (`DJANGO_DEBUG` or `DJANGO_ALLOW_SQLITE`) and tests, off in production. `MAX_BACKUP_UPLOAD_MB` is 30 by default (the uncompressed size of an uploaded backup). The server settings in section 5a (workers, threads, `--max-requests`, no `--preload`) are unchanged; memory levers are only applied after measuring and with the owner's approval.

## 5a. Server settings chosen for a small plan

- **Web server:** `gunicorn ... --workers 2 --threads 2 --max-requests 500 --max-requests-jitter 50 --timeout 60`. Two worker processes with two threads each, each restarted after about 500 requests to keep memory steady. There is deliberately no `--preload`.
- **Static files** (CSS and JavaScript) are served with hashed file names (WhiteNoise `CompressedManifestStaticFilesStorage`), so browsers can cache them for a long time and still pick up changes at the next deploy. `build.sh` runs `collectstatic`, which writes the list of hashed names. Tests use plain storage because they never run `collectstatic`.
- **Nightly job:** backup, then (only if the backup worked) the deleted-profile purge and the old edit-history purge, then `clearsessions` to remove expired logins. A `clearsessions` problem never hides a failed backup: the job exits with the backup result.
- **Backups:** only the newest 30 are kept (`BACKUP_KEEP_COUNT`), of every kind, and the pruning runs after every backup is made.
- **Edit history** is kept for `HISTORY_RETENTION_DAYS` (default 30) days.

## 6. Everyday safety habits

- Keep the Admin password in a password manager. Use unique passwords for every user.
- Turn on two-step login on your Render and GitHub accounts.
- Never share your Render or GitHub login. Create separate accounts in the app for others, through Admin.
- Look at the Backups screen once a week: the date of the last backup should be recent.
- Keep a monthly download on your own computer (section 3).

## 6a. Off-site copy of the backups (optional)

By default backups live inside the database. If the database host has a serious problem, they could be lost with it. An off-site copy puts each nightly backup in a separate storage account as well. It is off until you set the values below, and the app behaves exactly as before while they are empty.

1. Create a storage account with Backblaze B2 or Cloudflare R2. Both are S3-compatible and the first 10 GB is free on both; a diary of this size costs well under $1 a month.
2. Create a private bucket (never public). Create an access key that can only use that bucket, and note its key ID, its secret and the service address (for example `https://s3.us-west-004.backblazeb2.com`; R2 shows `https://<account>.r2.cloudflarestorage.com`).
3. On Render, add these environment variables to both the web service and the nightly cron job. Keep the secret only there, never in the code, an email or the repository.

| Variable | Meaning |
|---|---|
| `OFFSITE_BACKUP_ENDPOINT` | The service address, starting with https:// |
| `OFFSITE_BACKUP_BUCKET` | The bucket name |
| `OFFSITE_BACKUP_ACCESS_KEY_ID` | The access key ID |
| `OFFSITE_BACKUP_SECRET_ACCESS_KEY` | The access key secret |
| `OFFSITE_BACKUP_REGION` | Optional. Use `auto` for R2, or the region shown by Backblaze (for example `us-west-004`) |
| `OFFSITE_BACKUP_PREFIX` | Optional folder name inside the bucket |
| `OFFSITE_BACKUP_RETENTION_DAYS` | Optional. How long off-site copies are kept (at least 30, default 90). The newest copy is never removed |

4. After the next nightly run, the Backups screen shows "Off-site copy" with the last successful time. To test straight away, run `python manage.py backup_offsite` in the Render shell.
5. If a copy fails, every Admin sees a red warning at the top of each page and the Backups history shows the reason. A failed off-site copy never stops the normal backup.

Keep a bucket lifecycle or versioning rule off unless you want extra copies kept; the app removes old copies itself.

## 6c. Database storage (why the disk looks full, and how to shrink it)

**What uses the space.** Each nightly backup is stored inside the database as one compressed file, and the newest 30 are kept (`BACKUP_KEEP_COUNT`). Backups never contain other backups or the backup history. The real diary and fee data are usually a few MB, so a healthy database is normally tens or a few hundred MB. A very large size almost always means space that was freed by deleting rows (old backups, old edit history, sessions) but never handed back. PostgreSQL reuses that space for new rows, but only gives it back to the disk after a `VACUUM FULL`. Large backup files are stored out of line (TOAST), which makes this effect bigger.

**Steps**

1. Open the Shell of the web service in the Render dashboard and run `python manage.py db_storage_report`. It prints sizes and row counts only, never your data. Look at the database size, the largest tables, and "Sum of stored data" for the backups.
2. If the backups are small but the database is large, the difference is unreclaimed space. When nobody is using the site, run `python manage.py db_reclaim_space` (a dry run that changes nothing), then `python manage.py db_reclaim_space --confirm`. It locks each table for seconds to minutes, so pick a quiet time. Add other large tables from the report with `--tables name1 name2`.
3. Run `db_storage_report` again to see the new size.
4. To grow more slowly, lower `BACKUP_KEEP_COUNT` on the web service and the nightly job (for example 10 or 15), or rely on the off-site and emailed copies (sections 6a and 6a2) and keep few copies inside the database. Run the reclaim step again after lowering it.

The disk size of the database can be increased in the Render dashboard, but it usually cannot be decreased, so check the Render dashboard for what your plan allows before relying on it. If the size is still far above the report's figures after a reclaim, contact Render support.

## 6b. Final backup rehearsal (Milestone 7)

Do this once before relying on the system, and again after any large change.

1. In the Render shell run `python manage.py backup_rehearsal`. It takes a backup, reads it back and prints the record count per type, in the file and in the database. It must end with "Backup rehearsal OK". Any "DIFFERENT" line or an error means: stop and ask Kiro. It restores nothing.
2. On the Backups screen, download the newest backup to your computer.
3. Make a small harmless change (for example rename a test Item) and note it.
4. Restore the downloaded file on the Backups screen (a "Before restore" safety backup is made first).
5. Confirm your change is gone, the data is as it was, and you can still sign in. Create a new test user to check that numbering continues.
6. Run `python manage.py backup_rehearsal` again; it should say OK.

## 8. If you want to change hosts later

Because everything is in the database and the app can export a complete machine-readable backup, moving to another host (Railway or any other) means: set up the new host, restore the latest backup file there (upload it on the Restore screen), check, then point the address across. Your data is never trapped.
